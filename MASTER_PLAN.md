# embshift: Architecture and Engineering Master Plan

Zero-downtime vector database migration, shadow re-embedding, and dual-write engine.
Target: Zero-CGO single-binary Go engine (< 20MB RAM footprint) with embedded React 19 Migration Studio and shadow quality evaluator.

---

## 1. Problem Statement and Motivation

### 1.1 The Operational Problem of Vector Database Re-Embedding
In production retrieval-augmented generation (RAG) and semantic search systems, foundation embedding models evolve rapidly. Engineering teams regularly face a dilemma: production vector stores (Qdrant, pgvector, Milvus, Pinecone) remain locked into legacy embedding models (such as OpenAI text-embedding-ada-002 at 1536 dimensions), while newer models (such as text-embedding-3-large at 3072 dimensions, Voyage-3, or domain-adapted models) offer higher retrieval accuracy at lower costs.

Migrating an active vector database presents four technical obstacles:
1. Incompatible vector spaces. Unlike relational database column updates, vector spaces from different models cannot be compared mathematically. A query vector generated by Model B cannot compute cosine similarity against vectors generated by Model A.
2. Backfill throughput and rate limits. Re-embedding a corpus of millions of documents requires sustained API calls over many hours, consuming budget and risking HTTP 429 rate limit throttling.
3. Search availability. Shutting down the legacy index creates downtime for search and RAG workflows. Simple manual dual-writing during the backfill leads to race conditions, dropped updates, and state drift.
4. Retrieval quality verification. Teams lack automated tools to verify that the replacement index performs as expected against production query workloads prior to switching live traffic.

### 1.2 The embshift Solution
embshift is an autonomous vector database migration proxy and shadow re-embedding engine written in Go:
- Transparent dual-write proxy. Sits between application services and vector stores. Commits writes and deletes synchronously to the active primary store while asynchronously staging updates to the target store.
- Rate-limited backfill orchestrator. Iterates through legacy documents, generating replacement embeddings through controlled concurrency pools with token budget pacing.
- Production shadow query evaluation. Mirrors live queries to both the legacy and target indices, computing rank overlap (Jaccard similarity), Mean Reciprocal Rank (MRR), and NDCG in real time without increasing client latency.
- Phased canary traffic routing. Allows gradual read splitting (0% to 100%) with automated abort guards on error rate spikes.
- Dead-Letter Queue (DLQ). Sequewsters malformed or oversized poison-pill documents with live inspection and retry in the web studio.
- Prometheus observability. Exports `/metrics` for platform monitoring in Kubernetes and Grafana.
- Atomic zero-downtime cutover. Switches live routing to the target store once document parity reaches 100% and quality thresholds pass.
- Reversible rollback support. Keeps a reverse dual-write buffer active after cutover, allowing immediate rollback if retrieval anomalies appear.
- Embedded React 19 Migration Studio. Provides a single-binary web cockpit showing backfill progress, replication lag, spend against budget, and side-by-side search results.

## 3. Mathematical Formulation: Shadow Parity and Atomic Cutover

### 3.1 Document Parity Ratio (rho_parity)
Let D_legacy be the set of active document IDs in the legacy store and D_target the set of successfully embedded documents in the target store:

$$\rho_{\text{parity}} = \frac{|\mathcal{D}_{\text{legacy}} \cap \mathcal{D}_{\text{target}}|}{|\mathcal{D}_{\text{legacy}}|}$$

A migration phase is eligible for cutover only when rho_parity = 1.0 and dual-write replication lag is zero (Delta t_lag = 0).

### 3.2 Shadow Rank Correlation (R_shadow)
For mirrored production query q, let L_legacy(q) and L_target(q) represent the top-K retrieved document IDs:

$$\text{Jaccard@K}(q) = \frac{|L_{\text{legacy}}(q) \cap L_{\text{target}}(q)|}{|L_{\text{legacy}}(q) \cup L_{\text{target}}(q)|}$$

The system computes a rolling average semantic overlap across live production traffic, ensuring the new index demonstrates comparable or improved retrieval quality before enabling cutover.
